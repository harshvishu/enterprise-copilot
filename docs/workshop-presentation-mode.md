# Presentation in agent outputs

Real events and educational explanations are merged directly into **Requirements (Rhea)**, **Code proposal (Nova)**, **Review (Sentinel)** and **Release decision (Atlas)**. There is no separate Agent execution stream. Each section retains its completed steps beside its result. Requirements and Code Proposal start expanded; Review and Release are always expanded. Confluence and initial orchestration events appear with Requirements; human feedback and lifecycle events are routed to the relevant existing section.

Use the header **Presentation settings** gear to select **Normal speed** (the default), or 3, 3.5, 4, 5 or **10 seconds** per meaningful boundary. One shared playback cursor in `App` paces both the steps and when each result appears. **Skip remaining delays** beside Agent outputs reveals all received steps and eligible results immediately. A new run resets playback and skip. Preferences do not change the AI provider or backend execution speed.

**Follow latest output** defaults on. Each section scrolls its retained history to the newest presented event, and the page follows the current section/result. Pause follow in the gear for scrollback. Page following pauses while a human-input form or approval control has focus. Clarification, review feedback, approval and rejection become available from the actual server state without waiting for playback. The attention banner likewise reflects actual server state; the stage strip and agent results follow the presentation cursor. No extra status paragraph or progress bar is displayed.

## Source inspection and smallest change

The existing event path is Java agent/orchestrator → `PipelineEventPublisher.publish` → in-memory history and `SseEmitter` → `frontend/src/api.js:streamEvents` → `App.connect` → shared `useWorkshopPlayback` in `App` → the existing output components → inline `AgentActivity`. Late subscribers receive replayed history. Educational copy is attached inside each output section to these exact events; it does not publish extra events or audit records. `presentationPipeline` masks typed results until the latest corresponding completion is presented, including revision attempts; action handlers continue to use the original server context. `App` shares settings with the header gear. No new agent, backend service, API, dependency or persistence subsystem was added.

The source boundaries used for explanations are:

| Boundary | Responsible source under `backend/src/main/java/com/enterprise/copilot/` |
| --- | --- |
| Create, coordinate, save typed results, pause/resume | `orchestration/PipelineOrchestrator.java`, `domain/PipelineContext.java`, `persistence/PipelineStore.java` |
| Rhea analysis and local reference collection | `agents/requirements/RequirementsAgent.java`; `tools/ComplianceTool.java`, `ArchitectureTool.java`, `GitHistoryTool.java`, `ApiSpecificationTool.java`, `ToolResources.java` |
| Prepare prompts | `infrastructure/ai/PromptLibrary.java`: loads local `.st` files and replaces placeholders directly; this class does not use Spring AI `PromptTemplate` |
| Saved run mode, retries and configured fallback | `infrastructure/ai/RoutingAgentAiClient.java:generateForRun` |
| LIVE model request and structured output | `infrastructure/ai/SpringAiAgentAiClient.java:generate`: `ChatClient.prompt().user(renderedPrompt).call().entity(responseType)` followed by completeness validation; OpenAI or Ollama `ChatModel` |
| Scripted typed DEMO responses | `infrastructure/ai/DemoAgentAiClient.java`, `DemoResponses.java` |
| Nova proposal, never applied to disk | `agents/code/CodeGenerationAgent.java:generate`; `domain/CodeChangeSet.java` |
| Sentinel evidence preparation, review and findings | `agents/review/ReviewAgent.java:review`; `domain/ReviewDecision.java` |

| Human clarification, revision, approval/rejection | `PipelineOrchestrator.clarify`, `reviewFeedback`, `approve`, `reject`; `domain/audit/AuditService.java` |
| Simulated release lifecycle | `PipelineOrchestrator.deploy`: state changes, events and audit only, in both DEMO and LIVE |

The optional Confluence integration remains a participant exercise. The baseline does not call `ConfluenceAgent`. When wired in using the existing workshop markers, `PipelineOrchestrator.withConfluenceActivity` emits start/tool/completion around `ConfluenceAgent.gatherContext`, which calls `ConfluenceTool.lookup`. Only those received events produce Confluence explanations. A failed lookup does not produce a fabricated completion.

Reference collection uses direct Java calls to local resources; it is not vector retrieval or model-directed Spring AI tool calling. `AGENT_THINKING` is an existing event name for application work/request boundaries, not chain-of-thought. A request event alone does not mean a model completed successfully. Fallback events change subsequent educational copy to describe DEMO responses. Proposed tests and `testsPass` remain simulated/model-provided signals, not generated-test execution evidence. The inline histories label deployment transitions as simulated even in normal mode.

## Timing and verification

At the selected 3.5-second pace, a baseline successful run has 19 meaningful presentation boundaries: 16 through the approval request, then human approval, simulated deployment start and completion. The first step appears immediately; the 18 gaps budget approximately **63 seconds**. Human waiting and extra provider latency are excluded; if a hold has already elapsed during human waiting, playback takes less time. A real browser run measured **52.8 seconds through approval request + 7.7 seconds after approval**, approximately **60.5 seconds excluding human waiting**. Optional Confluence adds three boundaries (up to approximately 73.5 seconds total). Reference collection and gate evaluation each form one paced boundary per agent attempt; all individual tool/gate detail events remain visible. Revision, clarification and failures naturally have different lengths. Five-second pacing can exceed 75 seconds, and 10 seconds deliberately gives presenters a longer explanation interval; use 3 or 3.5 seconds for the target demo length.

Playback never sleeps in a backend thread or delays a model invocation, gate, HTTP action or test. Existing `PresentationPacer` configuration is unchanged, as is normal execution speed. Provider latency may exceed the presentation budget; playback waits for actual events and never fills time with invented work. Newly received events do not restart a pending presentation delay. Human waiting does not accrue presentation delays. Changing follow does not reset playback; choosing Normal speed reveals the recorded history and current results immediately. Explanations stay expanded at every speed.
